#### The part that matters most: generated output

A site generated by this toolkit redistributes the derived styling when it is
published, so the notices have to reach the user's repository too — not only this one.

They are placed **inside** `docs/stylesheets/extra.css`, not beside it. The CSS is the
derived artifact, so a notice in its header cannot be separated from what it
describes, cannot be lost when files are copied, and is served with the built site.
Verified: present in the source file and in the built `site/stylesheets/extra.css` of
this project and all three examples.

`check` enforces it — `attribution-removed` fires as a warning if the header is
stripped — and suggests, as a note only, a root `NOTICE` for discoverability.

## 3. Initial commit

Conventional Commits, `feat` for the initial feature set.

```text
feat: docs-studio v0.1.0, a generator for Zensical documentation sites

Scaffolds a documentation site that looks finished on the first build. The
design language is extracted from two documentation sites in production
(sisl/wm-physics-eval and sisl/ARIS.jl) and generalized into semantic colour
tokens mapped onto the theme's own variables, so a project changes its identity
through config rather than CSS.

Commands: init, check, update, presets, preview.

- init generates zensical.toml, the design-system stylesheet, a user-owned
  custom.css, starter pages, artwork and an optional GitHub Pages workflow, and
  never silently overwrites a file that is already there.
- check validates in three layers: universal structure (nav, links, anchors,
  assets, Pages sub-paths, markdown shape), language-specific fence parsing
  (Python, JSON and TOML with real parsers), then zensical build --clean
  --strict. Every diagnostic carries a file and line; errors exit non-zero.
- update regenerates managed styling from a checksum manifest. A managed file
  edited since generation is a conflict: reported with a diff, skipped, never
  overwritten, and it keeps its recorded hash so it stays a conflict until
  resolved.

Three palettes, custom palettes via a file or per-token overrides, and WCAG AA
contrast validated in both schemes before anything is written. A supplied logo
is copied byte for byte and never overwritten; with none, a deterministic
monogram is drawn from the palette and the project's initials.

A generated site makes no third-party requests: system fonts, no CDN, no maths
renderer.

Includes three example sites (Python, Julia and a project that is neither), the
toolkit's own documentation site generated by itself, and 254 tests covering
the CLI, config validation, colour arithmetic, rendering, validation, the
update contract, and the built wheel.

Licensed under Apache-2.0. The generated styling derives from the
documentation sites of sisl/ARIS.jl (MIT) and sisl/wm-physics-eval
(Apache-2.0); NOTICE records the derivation, the changes made, and the
upstream copyright and permission notices, which are also carried in the
header of every stylesheet the toolkit generates.

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

## 6. Changes made during release preparation

**A packaging bug the new CI job caught.** The sdist `exclude = ["examples", "docs"]`
added in the last round was not root-anchored, so it also excluded
`src/docs_studio/templates/docs/` — seven page templates. Because `uv build` builds the
wheel *from the sdist*, the released wheel lost them, and a cold install failed with
`TemplateNotFound: docs/page.md.jinja`. The existing packaging test used
`uv build --wheel`, which skips the sdist and so never saw it.

Fixed with `exclude = ["/examples", "/docs"]`, and the packaging tests now build the
full `uv build` path plus a new test asserting the sdist's own contents. This is
exactly the failure the cold-install job exists for, and it found it on its first run.

**A generated-workflow bug that self-hosting exposed.** The Pages workflow ran
`pip install "zensical==0.0.67" docs-studio`, which fails for every generated site
today, because `docs-studio` is not on PyPI — and would be circular for this repository,
which *is* docs-studio. The workflow now installs Zensical only, runs any
`deploy.extra_install` lines, and runs the checker when it is present:

```yaml
- name: docs-studio check
  run: |
    if command -v docs-studio > /dev/null; then
      docs-studio check --no-build
    else
      echo "docs-studio is not installed in this job, so the checker did not run."
    fi
```

This repository sets `extra_install = ["pip install ."]`. The strict build still gates
the deployment either way. Two tests cover it, and the three example sites picked up
the change through `update` with no conflicts.

**The three fence notes, fixed without weakening the check.** `css`, `yaml` and
`diff` are languages any documentation site legitimately uses, whatever it documents,
so they were not really "unexpected". Rather than widening each profile individually,
the profiles now share a `COMMON_FENCES` set — `bash`, `bibtex`, `console`, `css`,
`diff`, `html`, `json`, `text`, `toml`, `yaml` — and add their own language on top
(`python`/`pycon`, `julia`/`jlcon`).

The check is no weaker, and there are three new tests proving it: a mistyped
```` ```pyton ```` is still reported, `julia` on a Python site is still reported, and
the common languages now draw no comment. This site reports **0 notes**.

All three are fixes to existing behaviour, not new features.

**Two further defects found while doing the licensing work.** The `NOTICE` first
reformatted ARIS.jl's copyright line into a `Copyright:` field — MIT requires the
notice itself, so it now appears verbatim, and a test asserts it. And the earlier
`sdist` work had left the wheel-content test building with `uv build --wheel`, which
skips the sdist; the licensing tests build the real path.

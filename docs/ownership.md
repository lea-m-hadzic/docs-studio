# File ownership

A generator that rewrites your files is worse than no generator. `docs-studio` avoids
that by recording, for every file it writes, who owns it and what it looked like when
it was written.

## Two owners

**Managed** — styling and configuration, derived entirely from `docs-studio.toml`:

- `zensical.toml`
- `docs/stylesheets/extra.css`
- `.github/workflows/docs.yml`

These are regenerated by [`update`](update.md). You change them by changing the config,
not by editing them.

**Seeded** — content and artwork, written once and then yours:

- every `docs/*.md`
- everything in `docs/assets/`
- `docs/stylesheets/custom.css`

These are created when absent and otherwise never read, never rewritten, not even
under `--force`.

## The manifest

`.docs-studio/manifest.json` records a sha256 and an owner per file:

```json
{
  "schema_version": 1,
  "docs_studio_version": "0.1.0",
  "generated_at": "2026-10-22T16:40:00+00:00",
  "files": {
    "docs/index.md": { "sha256": "9f2c…", "ownership": "seeded" },
    "docs/stylesheets/extra.css": { "sha256": "4b71…", "ownership": "managed" },
    "zensical.toml": { "sha256": "e0a3…", "ownership": "managed" }
  }
}
```

That hash is the whole mechanism. It is what lets `update` tell *"unchanged since I
wrote it"* from *"the user edited this"*, and refuse the second.

!!! warning "Commit it"
    Without the manifest, `update` cannot tell a generated file from an edited one, so
    it treats **every** managed file as a conflict and writes nothing. `check` reports
    a missing manifest as a warning for exactly this reason.

Paths in it are POSIX-style and relative, so a manifest written on one platform is read
correctly on another.

## Why `custom.css` is seeded

The design-system stylesheet is managed, so editing it is a conflict. That is only
reasonable if there is an obvious place to put your own CSS instead — so every site
gets one, listed after the generated sheet:

```toml
extra_css = ["stylesheets/extra.css", "stylesheets/custom.css"]
```

Because it loads second, anything in it wins at equal specificity. Because it is
seeded, editing it is never a conflict, a palette change does not touch it, and
`--force` does not reach it.

As generated it is pure comment — zero CSS rules — so it cannot change how anything
looks until you write something in it.

## Files the toolkit does not know about

A file that is not in the manifest is not the toolkit's. `update` neither writes nor
deletes it, with one deliberate exception: a **managed path** that exists on disk but
is absent from the manifest is a conflict, not an overwrite. The toolkit did not write
that file, so it will not take it over.

## It never deletes

A page removed from the nav stays on disk. A monogram superseded by a real logo stays
on disk. `check` reports an orphaned page as a warning:

```text
  warning: docs/old-page.md: docs/old-page.md exists but is in no nav section, so nothing links to it [page-not-in-nav]
```

Removing it is your decision, not the toolkit's.

## What to commit

| Path | Commit? |
| --- | --- |
| `docs-studio.toml` | yes |
| `zensical.toml` | yes |
| `docs/` | yes, all of it |
| `.github/workflows/docs.yml` | yes |
| `.docs-studio/manifest.json` | **yes** — `update` needs it |
| `site/` | no; add it to `.gitignore` |
| `.cache/` | no; Zensical's build cache |

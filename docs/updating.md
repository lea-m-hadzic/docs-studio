# Safe updates

The contract, in one sentence: **a file the toolkit generated and nobody has touched
since is replaced; a file somebody has touched is a conflict, reported and left exactly
as it is.**

## What a run decides

| | on disk | action |
| --- | --- | --- |
| managed | absent | created |
| managed | unchanged since generated | replaced when the new render differs |
| managed | **edited** | **conflict** — skipped, reported, never overwritten |
| managed | not in the manifest | **conflict** — it did not write it, so it will not take it over |
| seeded | absent | created (this is how a page added to the nav appears) |
| seeded | present | left alone, always |

See [File ownership](ownership.md) for what managed and seeded mean.

## Look before you write

```bash
docs-studio update --dry-run
```

Prints the full plan and a unified diff per change, and writes nothing. Without
`--dry-run` nothing is written until you approve it, or pass `--yes`.

```text
docs-studio 0.1.0
  0 to create, 2 to update, 0 managed unchanged, 12 yours, untouched

   update  docs/stylesheets/extra.css
    --- a/docs/stylesheets/extra.css
    +++ b/docs/stylesheets/extra.css
    @@ -14,45 +14,45 @@
    -  --ds-primary: #4b5fd7;
    +  --ds-primary: #0f6e6b;
    …
   update  zensical.toml
```

`--verbose` also lists the files it is leaving alone, which is reassuring the first
time and noise after that.

## A conflict

```text
 CONFLICT  docs/stylesheets/extra.css — edited since docs-studio generated it
```

The diff shown is between what is on disk now and what the toolkit *would* have
written, so you can see what you would be giving up.

Nothing is written for that file. The rest of the update still goes through — a
conflicted stylesheet does not stop `zensical.toml` being brought up to date — and the
command exits 1.

!!! info "A conflict stays one until you resolve it"
    A skipped file keeps its **old** recorded hash in the manifest. Losing that would
    make the next update think the file was pristine and overwrite the edit, which is
    the exact failure this whole mechanism exists to prevent.

## Resolving a conflict

The right fix is almost always to move your rules out of the managed file:

```bash
# 1. see what you changed
docs-studio update --dry-run

# 2. move those rules into the file that is yours
$EDITOR docs/stylesheets/custom.css

# 3. let the managed file be regenerated
docs-studio update --force
```

`custom.css` loads after `extra.css`, so rules moved there keep winning. After that the
conflict is gone for good, because you are no longer editing a managed file.

If what you changed belongs in the config instead — a colour, a feature, a nav label —
change it there and the regenerated file will carry it.

## `--force`

```bash
docs-studio update --force
```

Applies conflicts too, overwriting what is on disk. It is the only way to lose an edit,
and the command says so before it does anything. For a file that is not in version
control, it is irreversible.

## When there is no manifest

```text
warning: there is no .docs-studio/manifest.json here, so every managed file that
already exists counts as a conflict. If this site was generated by docs-studio,
restore the manifest from version control.
```

This is the safe failure, not a bug: with no record of what it wrote, the toolkit
cannot distinguish a generated file from an edited one, so it assumes the worse of the
two and touches nothing.

## Upgrading the toolkit

A version change is announced:

```text
docs-studio 0.1.0 → 0.2.0
  0 to create, 3 to update, 0 managed unchanged, 12 yours, untouched
```

The managed files are re-rendered by the new version; your pages, your artwork and your
CSS are not involved. Read the diff, then apply.

## What a new nav entry does

Adding a page to `[[nav]]` and running `update` creates a starter page for it. Pages
that already exist are untouched, so this is also how you adopt a page you wrote by
hand: put it in the nav, and the toolkit records it as yours.

## Checking before you update

[`check`](check.md) warns about a managed file you have edited, before `update` is ever
run:

```text
  warning: docs/stylesheets/extra.css: a managed file has been edited since it was
  generated; `docs-studio update` will report it as a conflict rather than overwrite
  it [managed-file-edited]
```
